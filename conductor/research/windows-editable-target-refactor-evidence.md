# Evidence for a generic Windows editable-target resolver

Researched 2026-10-18 against primary Microsoft documentation. Proposal evidence only: no production code, input, screenshots, or document contents changed/read. Current implementation has `_focused_descendant`, a writable DataItem case, and `_excel_editor` guarded by EXCEL6/XLDESK. This note considers replacing that application exception with generic evidence.

## Verified API facts

### Focus has native and accessibility representations

`IUIAutomation::GetFocusedElement` retrieves the accessibility element with input focus; it can fail with ELEMENTNOTAVAILABLE when the element disappears, and Microsoft suggests graceful handling/retry. `GetGUIThreadInfo` independently retrieves GUI-thread information across process boundaries. Passing thread ID zero selects the foreground thread. Its `hwndFocus` identifies the native window with keyboard focus; `hwndCaret` identifies the window displaying the caret. Microsoft warns that returned handles may be invalid during activation changes. `GetFocus` by itself sees the calling thread's queue and is unsuitable for this cross-process lookup. [UIA focus](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation-getfocusedelement), [GetGUIThreadInfo](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getguithreadinfo), [GUITHREADINFO](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-guithreadinfo), [GetFocus](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getfocus).

`ElementFromHandle` retrieves the UIA element for a native window. UIA NativeWindowHandle is zero when the element has no HWND. UIA's tree and native HWND hierarchy are therefore different representations; a single native host can contain multiple accessibility elements. HasKeyboardFocus means current focus, whereas IsKeyboardFocusable merely describes the ability to receive it. [ElementFromHandle](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation-elementfromhandle), [UIA properties](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-automation-element-propids).

### MSAA can supply missing containing-window evidence

For native MSAA providers, UIA's LegacyIAccessiblePattern exposes the underlying `IAccessible`. `GetIAccessible` can return NULL for OLEACC proxy objects or UIA-to-MSAA bridge proxies; native UIA controls need not provide this pattern. `WindowFromAccessibleObject` returns the window **containing** the accessible object, or NULL if it is not window-contained. This is useful ownership evidence when NativeWindowHandle=0, but does not uniquely identify an accessibility child or prove focus/editability. [Accessing MSAA servers](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-accessingmsaaservers), [WindowFromAccessibleObject](https://learn.microsoft.com/en-us/windows/win32/api/oleacc/nf-oleacc-windowfromaccessibleobject).

`IsChild(parent, candidate)` checks native child/descendant relationships; equality requires its own comparison. It establishes window hierarchy, not accessibility focus. [IsChild](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-ischild).

Microsoft's SDK header declares LegacyIAccessiblePattern IID `828055ad-355b-4435-86d5-3b51c14a9b1b`. Counting the declared C vtable from IUnknown slots 0–2 places GetIAccessible at zero-based slot **26**, signature `HRESULT (..., IAccessible **ppAccessible)`. This is SDK declaration/order verification, not a live call. [Official SDK header, interface and vtable](https://github.com/microsoft/win32metadata/blob/main/generation/WinSDK/RecompiledIdlHeaders/um/UIAutomationClient.h#L8848).

### Tree traversal is available, but no documented universal recovery rule exists

Microsoft explicitly describes examining children or descendants of a focused element, recommends searching from a lower container rather than a large subtree, and notes that FindFirst/FindAll do not search ancestors. TreeWalker.GetParentElement provides ancestor traversal; the tree may change between calls. No cited source says the first focused descendant of an arbitrary ancestor is authoritative when providers expose contradictory focus. [Obtaining elements](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-obtainingelements), [GetParentElement](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationtreewalker-getparentelement).

### Writable value is broader than editable text

ValuePattern represents string-mapped intrinsic values and can describe a color picker. IsReadOnly=false therefore cannot authorize arbitrary text on every control. Edit controls can themselves be read-only or numeric. A ComboBox supports ValuePattern when it accepts arbitrary text; a DataItem must support it when its primary text is editable. These are stronger text-role contracts than unrestricted ValuePattern support, although provider correctness is still assumed. [ValuePattern](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-implementingvalue), [Edit](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supporteditcontroltype), [ComboBox](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportcomboboxcontroltype), [DataItem](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supportdataitemcontroltype).

TextPattern can describe read-only selectable text, so its existence is not a writable signal. GetSelection returns selected ranges or a degenerate insertion-point range; absence of selection is not sufficient evidence either way. IsReadOnly text attribute 40015 describes whether a range can be modified. GetAttributeValue returns special NotSupported/MixedAttribute objects where applicable, not a boolean; these must remain unknown rather than becoming false through coercion. Check the insertion/selection range rather than treating an entire mixed-permission document as one boolean. The last sentence is a design inference from range-level semantics. [Text patterns](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-implementingtextandtextrange), [GetSelection](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationtextpattern-getselection), [Text attributes](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-textattribute-ids), [GetAttributeValue](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationtextrange-getattributevalue).

TextPattern2.GetCaretRange supplies a zero-length caret range; isActive means the containing text control has keyboard focus. It does **not** document writable permission. TextEditPattern provides composition/autocorrection information and events, not a general SetText operation or a guarantee that the currently selected region is writable. Its presence supports a text-editing role, but current read-only/disabled/password checks still apply. [GetCaretRange](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationtextpattern2-getcaretrange), [TextEditPattern](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomationtexteditpattern), [TextEdit conventions](https://learn.microsoft.com/en-us/windows/win32/winauto/textedit-control-pattern).

## Reviewable design inference: constrained recovery without application names

Local metadata probe on 18 October 2026: resolving the observed EXCEL6 pane through the existing guarded helper produced a UIA editor with NativeWindowHandle=0. The LegacyIAccessible/GetIAccessible route produced no IAccessible object, so WindowFromAccessibleObject could not supply ownership for that editor. This is a live observation of the bridge being unavailable, not a general claim about Excel versions. GetGUIThreadInfo returned NULL focus/caret while the user was in chat; that part did not test active Excel focus. The proposed native/MSAA ownership route has therefore not demonstrated a complete replacement for the existing Excel exception.

Separate **which element receives input** from **whether that element accepts text**. Keep allowed/blocked/unknown outcomes and reasons; unknown is not equivalent to read-only and must not silently authorize injection.

1. Snapshot foreground HWND, native hwndFocus, and GetFocusedElement. Start from the direct UIA target and the UIA element for hwndFocus. Avoid names, titles, field values, and process-name allowlists.
2. If the direct target is a host, inspect focused descendants within that host. Prefer a unique focused text candidate over the host; preserve contradictions rather than trusting FindFirst ordering.
3. If native focus points to a host with no usable UIA child, inspect only a small, explicitly bounded ancestor neighborhood. For every recovered candidate require HasKeyboardFocus and a containing HWND resolved from NativeWindowHandle or native MSAA. Candidate HWND should equal hwndFocus, or be a native descendant of hwndFocus for a nested-host case. Reject a containing HWND that is merely a broad ancestor/sibling of hwndFocus: matching the top-level window alone would allow stale Copilot focus while editing a cell.
4. Run capability checks independently: enabled, password policy, text-role evidence plus explicit writable ValuePattern, or an active text range with boolean IsReadOnly=false. Preserve explicit read-only/disabled results. An active caret is corroboration of focus, never permission. Missing/contradictory capabilities remain unknown.
5. Recheck foreground/native focus before returning and again before insertion; retry once on a detected change, otherwise reject stale state. Do not SetFocus, press F2, or use test typing as detection.

These steps are a proposed policy assembled from the APIs, **not** Microsoft's published algorithm. Even exact containing-HWND equality only corroborates ownership: multiple accessibility objects can share the same host. **Experiment gate before replacing EXCEL6/XLDESK:** record only focus flags, IDs, roles, patterns and HWNDs for active cell editing versus stale Copilot candidates; verify the native/MSAA route distinguishes them. If both resolve to the same host, the route is insufficient and the proposal must change. No documentation guarantees the desired Excel mapping.

Strict native ownership will have false negatives for native UIA providers lacking an HWND bridge, popup-based editors, and unusual embedded hosts. Do not weaken it to top-level membership. An ancestor search needs depth/result limits and a latency budget; checking time between calls is not a hard timeout on a hanging COM provider. Exact bounds require measurement.

Suggested verification: an MSAA editor with HWND=0, an embedded WebView text editor, stale focused sibling, two focused candidates, focus changing during traversal, ordinary read-only text, protected document region, writable color picker, non-editable ComboBox, disabled/password target, and unsupported/mixed attributes. No document content is needed for unit fixtures.

## Alternative: real TSF text service

TSF mediates document text access between enabled applications and text services. A text service is a COM **in-process server** registered with TSF, not simply an external process querying focus. It obtains contexts through the TSF manager; changes require an edit session whose document lock is negotiated with the application. This offers a substantially stronger text-edit contract within TSF-enabled applications. [Architecture](https://learn.microsoft.com/en-us/windows/win32/tsf/architecture), [Why TSF](https://learn.microsoft.com/en-us/windows/win32/tsf/why-use-text-services-framework), [Edit sessions](https://learn.microsoft.com/en-us/windows/win32/tsf/edit-sessions).

Deployment includes COM registration, TSF service registration, language profiles and categories; Microsoft recommends signed binaries. Supporting both 32-bit and 64-bit applications requires parallel DLLs and independent registrations under the same CLSID. A mismatched-bitness service may fail to load silently. This is a native component/installer/lifecycle project; communication with the existing Python dictation process and recovery from service crashes would need design and testing. That project-size assessment is an inference, not an API requirement. [Registration](https://learn.microsoft.com/en-us/windows/win32/tsf/text-service-registration), [64-bit considerations](https://learn.microsoft.com/en-us/windows/win32/tsf/64-bit-platform-considerations).

TSF is not established here as universal coverage for non-TSF controls. Calling TF_GetThreadMgr in the external app obtains only its calling-thread manager. Modern Win+H documentation describes user behavior and Azure recognition but does not disclose an equivalent public editability detector. Historical Vista WSR used TSF; this does not establish modern Win+H internals. [TF_GetThreadMgr](https://learn.microsoft.com/en-us/windows/win32/api/msctf/nf-msctf-tf_getthreadmgr), [Win+H](https://support.microsoft.com/en-us/accessibility/windows/use-voice-typing-to-talk-instead-of-type-on-your-pc), [Historical WSR](https://learn.microsoft.com/en-us/archive/msdn-magazine/2007/july/speak-up-support-dictation-with-text-services-framework).

Unproven: a universal UIA detector, the correct generic bounds, Excel's actual MSAA containing-HWND mapping, full native ownership coverage across WebView2 versions, provider consistency, and equivalence to Win+H. A proposal can improve evidence and remove class-name exceptions without promising those properties.
